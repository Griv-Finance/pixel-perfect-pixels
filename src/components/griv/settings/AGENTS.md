# Settings module rules
- Settings is one directory at `/settings` plus one dynamic page `/settings/$slug`: every setting (name, category, search keywords, edit permission) is listed once in `src/lib/settings/registry.ts`, each slug maps to a page in `src/components/griv/settings/pages/index.tsx`, and pages are built from `src/components/griv/settings/ui.tsx` (SettingsPage, Section, Row, ToggleRow, useDraft + SaveBar, useTab), so new settings need no new route files and stay consistent.
- Settings sample data lives in `src/lib/demo/settings/`: `access.ts` owns roles, members and `can()`/`useCan()` (the "Preview permissions as" switch changes the acting member; read-only pages come from the registry's edit permission; a real backend must still enforce permissions server-side), and every settings change appends to the Security history / Audit log stores in `activity.ts`.
- Developer settings (API keys, webhooks, IP rules, API logs) are environment-specific: pages show only `forEnv(rows, envOf(live))` from the header's Test/Live switch, never a second switch, and secret keys are shown once at creation and stored only as their last 4 characters.
- Security, verification and connection actions that need a real service (password change, adding 2FA methods or passkeys, recovery codes, integrations, email/SMS sending) validate input and then say honestly that nothing was done; uploaded compliance documents go to "In review" and are never marked verified client-side.
