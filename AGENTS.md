# Project rules
- Merchant-group dashboards are standalone full pages under `/merchant-groups` (data in `src/lib/merchant-groups.ts`, UI in `src/components/griv/merchant-groups/`) with their own layout; they never render inside or change the real app layout `AppShell`, so proposals can be compared without affecting the product.
- Preview menus may only list features that exist in the real app menu; a test enforces this so mockups never imply features Griv lacks.
- Standard dashboard pages render through `DashboardPage` (real `AppShell` + breadcrumbs + sample-data notice) and build UI from `src/components/griv/kit`; page-specific code lives in `src/components/griv/pages/<slug>/` and sample data in `src/lib/demo/`, so all pages stay visually consistent and easy to wire to a backend later.
- The dashboard is one unified, MailerLite-inspired page (no state switcher): an onboarding checklist that hides when done, then a Performance overview card whose grey-headed sections (Payments, Balances & settlements, Payment links, Invoices, E-commerce) share one period + currency selector. Data and metric helpers live in `src/lib/demo/dashboard.ts`, UI in `src/components/griv/pages/dashboard/unified/`; flows that don't exist open an honest "not wired up in the demo" dialog.
- The Transactions page follows the MailerSend Emails-page pattern: `Show for:` type selector, one filter container with More/Less filters, count + Export toolbar, soft status badges with dark failure-reason tooltips, and its own pagination footer (default 25 rows). Transaction data helpers (provider, internal TXN id, origin, reasons, filters, pagination) live in `src/lib/demo/unified.ts`.
- There is no backend yet: data shared across pages (balances, catalogue/stock) lives in in-memory stores from `createDemoStore`, so actions on one page (e.g. a POS sale) show up on others.
- Demo money movements (transfers, payouts, refunds, non-cash POS payments) must never reach a final success state client-side; they stay pending until a real server/provider confirms, so the UI never fakes a completed financial operation.
- Balances has two designs side by side: the original at /balances and a Transactions-style preview at /balances-preview; both use the same balances data and are linked to each other from their headers, so designs can be compared without touching the live page.
- Status colours come only from `src/lib/status.ts` and money formatting only from `src/lib/money.ts` (amounts are never summed across currencies).
- The Payment Link details page is one adaptive Stripe-style page (`src/components/griv/pages/payment-links/link-detail/`): Products/Details rows come from `src/lib/demo/link-details.ts` helpers driven by the link's pricing model; per-link note, metadata, payment methods and ship-to live in that file's extras store so builder saves never wipe them.
- Create/Edit Payment Link is a full-screen two-column workspace (routes `/payment-links/new` and `/payment-links/$linkId/edit`, UI in `src/components/griv/pages/payment-links/builder/`, model in `src/lib/demo/link-builder.ts`) with a live checkout preview; the whole builder config is saved on `PaymentLink.config` and mapped back onto the legacy fields by `configToLink`, so edits stay lossless and the list/details pages keep deriving from the legacy fields. Never open the old LinkForm dialog — it was removed.
- The Invoice Details page is one Stripe-style page at `/invoices/$invoiceId` (`src/components/griv/pages/invoices/detail/`, helpers in `src/lib/demo/invoice-details.ts`): status-aware header actions, separate lifecycle / payment / delivery statuses, a document preview, activity with team notes, payments (externally recorded ones stay pending), credit notes capped at the paid amount, Logs/Events and Details/Metadata. The listing, editor and this page share `invoicesStore` (`src/lib/demo/invoices.ts`) so they stay in sync. Download PDF builds a real PDF with pdf-lib (`src/lib/invoice-pdf.ts`, A4 or Letter), writing money as `NGN …` because standard PDF fonts have no ₦ glyph.
- Create/Edit Invoice is a dedicated two-column workspace inside the app shell (routes `/invoices/new` and `/invoices/$invoiceId_/edit`, UI in `src/components/griv/pages/invoices/builder/`, rules in `src/lib/demo/invoice-builder.ts`) that edits the same `Invoice` record — no separate form model. Every view (editor preview, review PDF/email/payment page, PDF file, details page) uses the one `invoiceTotals` model, and taxes come from the configured rates in `src/lib/demo/tax-rates.ts`, never a hardcoded rate. Only Draft/Scheduled invoices are editable; drafts autosave; finalizing never marks an invoice paid and its email stays "Sending" because no email service exists. The old InvoiceEditor dialog was removed — never reintroduce it.
- Brand logos are real PNG files in `public/brand/` referenced by absolute path (not `.asset.json` CDN pointers), because the app is also deployed to Vercel, which cannot serve Lovable CDN asset URLs.
